# 前端改善建议与洞察接入任务书

本文件可直接交给负责前端的模型实施。本轮没有修改前端文件。目标是让业务完成“发现问题 → 看懂原因 → 核对证据 → 测试调整 → 留下结论”，同时沿用当前网络图、聚类、筛选和推演。

## 1. 产品判断

当前系统已经具备计算与展示能力，主要体验缺口是：指标很多，但没有明确告诉用户“当前应该关注什么、为什么、下一步做什么”。增加一个聊天框并不能自动解决这个问题。建议先把编码洞察做成稳定的决策入口，再让大模型在同一组事实之上支持追问。

本轮后端已提供 `GET /api/insights`。它返回实际计算支持的中文结论、证据和可执行推演请求，不依赖外部模型。界面建议命名为“业务洞察”，展示“规则生成 · 可核验”；只有真正接入外部模型时才标记模型生成内容。

## 2. P0：选中编码后，先看到结论

沿用现有 `#detail-panel` / `#detail-body` 选中编码面板，在原始指标之前增加洞察区域，不改变图上的单击、双击和聚类行为。

建议阅读顺序：

1. 编码、名称、当前预测版本/月/口径及“基线/情景”标签。
2. 一句结论 `headline`，搭配状态文字；不只用红绿颜色。
3. 供应方/需求方两张摘要：自己能否覆盖相关上层；相关下层是否存在全局总量不足。
4. 最多三条优先事实，顺序为实际缺口、未来缺口、下层缺口；数据未知必须同时可见。
5. “查看依据”“模拟调整”“查看下层风险”操作。
6. 可展开的月份趋势、需求贡献、加工地与周期证据。

示例表达应使用接口原文或数值：

> 当前供应不能覆盖上层折算需求。可用产出 900，上层需求 1000，预测缺口 100。点击“模拟增加 100 产出”查看调整后对自身和下层的影响。

以上仅说明表达方式，具体数值必须来自所选编码，不能写死。库存覆盖、未来缺口及下层风险由对应事实决定，不自行补出没有数据支持的结论。

## 3. 可直接使用的接口

```text
GET /api/insights?code=A&version=2026-09-10&month=2026-09&mode=cross&source=forecast
GET /api/insights?code=A&scenario=<情景ID>&month=2026-09&mode=cross
```

`code` 必填。可用参数为 `revision/version/month/mode/source/scenario/span`；`span` 是从所选月份开始的洞察窗口，默认最多12个月且不超过已知预测窗口，显式指定时不能超过120。传 `scenario` 后由后端固定其基线修订号及预测版本。完整真实样例见 [insight-example.json](insight-example.json)，样例中的构建 ID 和情景参数不可直接当作当前生产数据使用。

| 字段 | 推荐呈现 | 语义约束 |
| --- | --- | --- |
| `status` / `headline` / `summary` | 结论区 | status 为 risk / unknown / attention / covered，属于解释状态，不是延误概率 |
| `generator` | “规则生成 · 可核验” | 当前 `llmUsed=false`，不可假装调用了大模型 |
| `trace` | 常驻版本和口径标签 | 包含 revision、buildId、version、month、mode、source、scenario |
| `facts[]` | 结论卡与展开证据 | 每条包含稳定 id、level、text、evidence；引用 evidence 字段，不从文案反向解析数字 |
| `confidence` | “哪些已确认 / 哪些未知” | 这是数据完整性，不得转换成“置信度90%” |
| `scopeComparison[]` | 三口径小表 | 三行不能相加；没有BOM上层时 applicable=false |
| `demandContributors` | 上层贡献排序条形图/表 | 前10项、总项数、截断标记；shareOfKnownDemand 是已知贡献占比，不是缺口责任比例 |
| `dependencies` | 当月下层缺口列表 | 每个 gap 是该下层对全部相关上层的总缺口，不是分配给当前编码的量 |
| `horizon.timeline` | 本编码未来供需曲线 | 横轴明确月份，null 用断点/未知，不画成0；当前依赖列表是所选当月，不是全部未来月份 |
| `horizon.cumulative` | 起始库存＋窗口累计覆盖 | 只加一次起始库存；不宣称日级供货、停线日期 |
| `actions[]` | 可操作的下一步 | 根据角色显示/禁用；先填入推演表单，再由用户发起模拟 |
| `evidenceLinks` | 查看原始明细/网络 | 带上给定的追溯参数，避免点击后变成另一个月份或版本 |

### 推演准备与执行

进入“异常推演”或用户展开“模拟调整”时，可后台调用一次：

```text
POST /api/scenarios/prepare
{"revision":1,"version":"2026-09-10","month":"2026-09"}
```

返回202后按既有 `/api/jobs/{id}` 轮询。此动作把基线装载到独立推演线程，不创建情景、不修改预测。在同一 revision/version 下避免重复调用。展示“正在准备推演数据，可继续浏览”；准备完成后再展示“推演已就绪”。切换版本后需重新准备，不能永久缓存就绪状态。

点击 `test_supply_increase` 时，将 `actions[].request` 填入现有推演表单，经业务确认再 POST `/api/scenarios`。提示这只是总量平衡的测试值，尚未验证真实产能；增加该编码预测，也会提高它作为使用方对下层的需求。现有情景不会返回直接加量动作，避免把情景增量错误地套到原始基线。

## 4. P0：交互和错误恢复

- 切换编码时立刻更新选中态和面板标题，为洞察保留稳定空间；超过短暂等待再出现局部加载提示，避免整个页面遮罩。
- 洞察与图谱请求分别加载，洞察失败不隐藏已成功的网络图。错误卡提供“重试”，保留已经选择的编码和筛选条件。
- 使用 `AbortController` 取消过期请求；用完整查询键比对结果，旧编码A的迟到响应不得覆盖新编码B。查询键至少包含修订号、预测版本、月份、口径、来源、情景、编码。
- UI 不应每次操作同时刷新全网图、报告、明细及所有月份。需要哪个面板才加载哪个数据；详情和洞察可分别加载。
- 缓存只在相同查询键下复用；收到新 revision 后使旧基线缓存失效，保留旧情景自己的版本标签。
- 429显示队列繁忙，允许有退避的重试；504显示执行超时并建议缩小范围；503显示装载/恢复状态；409提示版本已变化。不要无限自动重试写操作。
- 错误详情保留响应头 `X-Request-ID` 或 `error.requestId` 供反馈定位。技术标识放在“问题详情”，不要挤占业务结论区域。
- 动态状态使用合适的 aria-live 提示，键盘可以访问关键按钮、关闭面板和返回原位置；焦点不能被滚动或自动刷新抢走。

## 5. P0：把网络图变成问题入口

默认给出“待处理问题清单”，用户可从编码、月份、缺口和证据进入网络；网络图负责理解关联。不要为了“高级感”一次绘制12万个节点。

当前图接口有节点和边上限，必须展示“当前显示X个 / 全部Y个，已按范围截取”。不能把截取后的图称为完整供应网络，也不能把聚类凸包等同于真实供应分配。

保留已有产业、加工地聚类，明确“多加工地编码可能属于多个加工地组”。区分月度单一加工地与整个预测窗口单一加工地；把“独家”描述为“当月计划单一加工地”，除非另有正式产能资格主数据支持。

选中编码后固定当前位置和缩放；开关洞察、展开证据、模拟完成不应无故重新运行布局。风险路径、关键路径应有文字说明和图例，不能仅用颜色区别。

## 6. P1：真正提高决策效率的下一批能力

以下是产品建议，不应被前端模型误认为已有对应后端字段：

| 建议 | 业务价值 | 当前依赖/边界 |
| --- | --- | --- |
| 预测版本变化解释 | 回答“本月为什么比上一版更危险” | 需新增按同编码/月拆分供应、上层预测、BOM及配置变化的比较接口；不能只比较两个总缺口就归因 |
| 跨月下层风险扫描 | 提前发现当前充足、未来不足的依赖 | 当前洞察下层列表针对所选当月；需要额外的窗口扫描及结果缓存 |
| 关注清单、负责人和复核状态 | 把风险转成可跟踪工作 | 需用户级身份、关注/备注/复核存储；此轮未实现 |
| 计量单位与风险排序 | 避免不同编码单位混杂时直接比较数量大小 | 需导入明确单位或转换关系，再设计缺口率/影响面等排序；禁止跨编码直接相加缺口 |
| 供应能力验证 | 区分预测可增加和实际能增产 | 需产能、设备、班次、合格加工地及采购约束数据 |
| 时间对齐的长期风险 | 判断长周期子件应提前哪个月准备 | 当前是同月预测匹配＋周期路径提示；需明确投料/完工时点、运输和工作日历后才能做时移需求 |
| 指令短期风险 | 从月度计划过渡到真实短期履约 | 需库存基准、指令完工时点、投入/在制/收货和日历；当前MO仍按月聚合 |
| 企业级协同 | 员工级审计、权限与通知 | 当前是角色令牌身份；需企业认证、组织隔离、任务负责人配置 |

不要在现有数据上生成“确定停线日期”“延期概率”“建议分配给上层多少”或“某个产业故意低报”等结论。系统目前没有支撑这些判断的数据或分配模型。

## 7. 大模型接入方式

现有工具目录 `/api/ai/tools` 已增加 `summarize_code`，通过 `/api/ai/invoke` 与页面共享同一组洞察。

建议分两层：第一层由后端负责计算事实、追溯版本和提出可测试假设；第二层由大模型解释事实、组织问答及选择查询工具。模型回答中的数值必须能回指 `facts[].id/evidence` 或其他API结果。用户没有指定编码/月/口径时，应从当前界面上下文继承并明确显示，而不是自行猜测。

如果后续接外部模型：调用在服务端完成，不把密钥放入浏览器；只发送所需的有限证据，不发送整份BOM/预测表。模型不可覆盖数值事实、把未知补成0、擅自修改基线或执行产能分配。外部模型超时后仍显示规则洞察；问答是增强能力，不能成为查看风险的前置条件。本轮未配置外部模型供应商或密钥。

可用追问示例：

- “这100的缺口怎么折算出来的？” → 贡献清单＋BOM系数。
- “它自己的供应充足，为什么仍有风险？” → 下层总量风险/未来月份/加工地与周期事项。
- “把供应增加到需求量会怎样？” → 填入返回的独立推演请求，执行后解释全链路变化。
- “是哪个上层虚高了？” → 给出上层贡献和版本变化证据，明确需要业务核对计划依据。

## 8. 给前端模型的验收清单

1. 缺口为100的样例显示100；点击依据后能看到同一版本的BOM折算与上层贡献。
2. 缺库存仍能展示已确认的预测缺口；库存未知不自动填0，不把预测匹配判断全部禁用。
3. 顶层编码不显示“供应过剩”；存在下层总量不足时明确提示，并说明未分配。
4. A、B快速切换，A迟到响应不能覆盖B；基线/情景、三种口径和月份切换均不串缓存。
5. 所有操作沿用返回的trace；模型与页面展示相同数字。
6. 只读用户能看洞察，不能执行推演；planner能准备和运行推演，不能发布基线。
7. 模拟加量只修改独立情景；结果回到网络图后清楚标记情景，允许回到基线。
8. 429/503/504和导入失败均有恢复方式，图谱和导航不被全局加载锁住。
9. 聚类、下钻、关键/风险路径、缩放位置保持兼容；图谱截断有明确标识。
10. 全部结论可展开证据；AI未接入时如实显示规则洞察，不用虚构概率或抽象分数制造可信感。
