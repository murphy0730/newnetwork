# 网络图地图化缩放与信息详略自适应设计

本文件是设计方案，**不改变业务算法与数据口径**。目标：让供应网络图在万级至十万级编码下
具备"像地图一样"的缩放体验——放大看编码细节，缩小看聚合全貌，且**所有汇总数字始终正确**。

现状基线：G6 v5.1.1（Canvas 渲染）、自研分层布局 `layered()`、凸包 overlay 独立 SVG 层。
生产规模：12 万编码 / 59.4 万 BOM 边 / 132 万预测行 / 10 层 / 300 加工地
（见 `docs/后端深度审查与性能验证.md`）。

---

## 0. 结论先行

**能做，且不需要重写布局。** 关键地基已经在代码里：`layered()`（`forecast-graph.js:7-41`）
已经把**全量节点坐标一次性算好并缓存在 `_presetMap`**（`:364-371`），且该纯函数在 10 万节点上
验证过位置计算。所以缺的不是坐标系，而是**一层"看什么"的调度**。

差异在于两个语义：

| | 现在 | 地图化之后 |
| --- | --- | --- |
| 缩放的语义 | 改变"显示多大" | 改变"**显示什么**" |
| 渲染集 | 全量（12 万 + 59.4 万） | 视口内 × 当前层级，预算 ≤ 3000 |
| 坐标 | 每次操作重算、位置全变 | 只算一次，缩放不动坐标 |
| 聚合 | 无 | 超节点 + 聚合边，计数守恒 |

## 1. 瓶颈实证（先对齐事实，再谈方案）

### 1.1 图元占比（12 万节点 / 59.4 万边）

| 图元 | 数量 | 占比 | 来源 |
| --- | ---: | ---: | --- |
| 节点圆 | 120,000 | 8.4% | `:122` type: 'circle' |
| 节点标签 | 120,000 | 8.4% | `:129` labelText: d.id |
| 边线 | 594,000 | 41.6% | `:142` type: 'line' |
| 边箭头 | 594,000 | 41.6% | `:143` endArrow: true |
| **合计** | **≈1,428,000** | 100% | |

**结论：边与箭头占 83%，标签只占 8.4%。优化优先级必须按这个比例排，不能按"感觉上标签最显眼"排。**

### 1.2 四个全量卡点

| # | 位置 | 问题 | 触发时机 |
| --- | --- | --- | --- |
| 1 | `:412-415` | `_applyStates()` 构造 71.4 万个状态 key 并全量 `setElementState` | **每次点击节点** |
| 2 | `:143` | 边箭头全量渲染（59.4 万个） | 常驻 |

| 4 | `:263` / `:294` | 凸包每帧清空重建 SVG，且逐成员两次坐标 API 往返 | 聚类开启时拖拽 / 缩放 |

### 1.3 已确认的代码事实（避免重复踩坑）

- `select()`（`:477`）**全库无调用点，是死代码**。点击路径是
  `node:click`（`:181-197`）→ `chainCode = id` → `_applyStates()`。
  **不要试图优化 `select()`，收益为 0。**
- `_usePreset()`（`:362`）`layoutMode === 'layered' || nodes.length > 800`。
  > 800 节点时 `preset` 恒为 `true`，故 `combo-combined` 分支不可达（不会"布局数秒"）；
  > 但也因此**"力导向"按钮在 >800 节点时完全失效**——这是一个需要一并修掉的假开关。
- `vendor/g6.min.js` 已打手工补丁（`mutationRecords` 循环追加替代 `push.apply`，避免万节点
  超调用栈）。**升级 G6 需重打补丁**，见 `docs/多选筛选与完整BOM分层说明.md` 第 37 行。

## 2. 不变式（硬约束，先立规矩再设计）

以下五条在改造全过程中不可违反，任何一条被破坏即视为方案失败：

1. **坐标系不变**：缩放、平移、切层级、开关面板，都不得改变节点的世界坐标。
2. **口径不变**：`mode` / `source` / `version` / `month` / `span` 的语义与现有实现完全一致，
   本方案不新增、不修改任何业务计算。
3. **计数守恒**：聚合块的数字必须等于其成员的真实计数，且与后端同源。
4. **数量不可加**：缺口、供应、需求绝对值**跨编码禁止相加**
   （依据 `docs/前端改善建议与洞察接入任务书.md` §6）。聚合块只允许显示
   个数 / 最大值 / 占比 / 分布，不得显示"缺口合计"。
5. **双向一致**：图上任何数字必须等于汇总表、洞察面板在同一 `trace` 下的数字。
   出现"图上说 37 个风险、汇总表说 41 个"即为致命缺陷。

## 3. 架构：一层 LOD 调度器

改造点集中在**一个插入层**，不动上下游：

```text
后端 /api/graph ──► setData(nodes, edges)          ← 不改
                          │
                          ▼
                  ┌───────────────────┐
                  │  世界坐标系（一次）  │  layered() 已有，缓存在 _presetMap
                  └───────────────────┘
                          │
                          ▼
              ┌─────────────────────────────┐
              │   LOD 调度器（新增，唯一入口）  │
              │  · 读 scale → 定层级           │
              │  · 读视口 → 算可见集            │
              │  · 产出：渲染集 + 聚合集         │
              └─────────────────────────────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
     addNodeData / removeNodeData   凸包 overlay
        （增量，非全量 setData）      （只画可见成员）
```

**关键设计原则**：调度器是**纯函数**，输入（全量数据 + 世界坐标 + 视口 + scale），
输出（渲染集）。纯函数意味着可单测、可回放、可离线验证——这是让"计数守恒"可证的前提。

## 4. 详细设计

### 4.1 四档位层级定义

| 层级 | scale 区间 | 画什么 | 对象预算 | 标签策略 |
| --- | --- | --- | ---: | --- |
| **L0 战略层** | ≤ 0.25 | 加工地 × BOM 层聚合块 + **关键路径骨架常显** | ≤ 400 | 聚合标签（组名 · N 编码 · M 高风险） |
| **L1 聚合层** | 0.25 – 0.6 | 聚合超节点 + 聚合超边 | ≤ 1500 | 仅超节点标签 |
| **L2 网络层** | 0.6 – 1.2 | 真实节点全出，**仅高风险 / 关键路径 / 选中节点带标签** | ≤ 1200 | 选择性标签 |
| **L3 编码层** | > 1.2 | 全标签 + ×配比 + 加工地角标，视口外剔除 | ≤ 800 | 全标签 + 碰撞剔除 |

补充规则：

- **临界迟滞**：进入阈值与退出阈值错开（如 L1→L2 在 0.6 进入、0.52 才退出），
  避免在边界处来回抖动导致反复切换。
- **切换去抖**：`aftertransform` 触发后 120ms 无新事件才执行切换
  （**注意：G6 v5.1.1 bundle 内无 `viewportchange` 事件，只有 `aftertransform` / `beforetransform`，
  现有代码 `:158` 已在用，LOD 判定挂这里**）。
- **缩放过程中不切换层级**：只在用户停止缩放后判定一次。

### 4.2 视口裁剪（省掉 83% 图元的核心手段）

已实证可用的 G6 v5 能力：

| API | 存在 | 用途 |
| --- | --- | --- |
| `getCanvasByViewport` | ✅ | 视口矩形 → canvas 坐标，**与 preset 坐标同系，可直接比较** |
| `getZoom` | ✅ | 读当前 scale |
| `getViewportCenter` | ✅ | 平移后重算视口 |
| `zoomTo` / `focusElement` | ✅ | flyTo 下钻与定位 |
| `addNodeData` / `removeNodeData` | ✅ | **增量增删节点** |
| `addEdgeData` / `removeEdgeData` | ✅ | **增量增删边** |
| `getViewportSize` | ❌ 不存在 | 视口尺寸改用 `el.clientWidth/clientHeight` |

实现要点：

1. 视口矩形 = `getCanvasByViewport([0,0])` 与 `getCanvasByViewport([w,h])` 两点求得，
   **一次算完，不要逐节点调 API**（这正是凸包 `:294` 现在的错误做法）。
2. 可见集 = 节点 preset 坐标落在"视口矩形 × 1.25 缓冲"内。缓冲区防止平移时边缘闪烁。
3. **跨视口长边保底**：边的包围盒与视口相交即保留，即使两端都在视口外。
   地图上对应"跨区域道路"，这是保持全局连通感的关键，不能按端点简单裁剪。
4. 集合差量更新：`可见集 - 已渲染集` → `addNodeData`；`已渲染集 - 可见集` → `removeNodeData`。
   **绝不在缩放过程中调 `setData()`**（那会触发 `render()` 全量重排）。
5. **孤立点提前过滤**：延用现有 `hideIsolated` 语义（`:490` 设置项），在调度器入口过滤，
   而不是渲染后再隐藏。

### 4.3 标签分级（8.4% 图元，顺手拿下）

bundle 内已确认存在但**当前未注册**的 behavior（`:151` 只有
`['drag-canvas', 'zoom-canvas', 'drag-element']`）：

| Behavior | 作用 | 建议 |
| --- | --- | --- |
| `auto-adapt-label` | 标签随元素尺寸自适应，放不下则隐藏/收缩 | L1–L3 注册 |
| `optimize-viewport-transform` | **视口变换期间降级渲染**，专为地图手感设计 | 全局注册 |
| `fix-element-size` | 缩放时元素保持固定像素尺寸 | L3 可选（标签可读性） |

策略：**按层级显隐标签**，而不是单纯依赖 behavior：L0/L1 只给超节点标签；
L2 只给高风险 / 关键路径 / 选中节点标签；L3 全标签 + 视口内碰撞剔除
（简单网格占位法即可，O(N)）。

### 4.4 边与箭头降级（83% 图元，最高优先级）

| 层级 | 边策略 |
| --- | --- |
| L0 | 只画**关键路径骨架**与风险走廊，`endArrow` 关闭 |
| L1 | 聚合超边，线宽 ∝ 组间连接对数，`endArrow` 关闭 |
| L2 | 真实边，`endArrow` 开启，但只画可见集内（含跨视口长边） |
| L3 | 真实边 + 箭头 + 配比标签 |

要点：**`endArrow` 是高成本项**（每条边一个独立 Path 图元）。在低层级关闭，
高亮路径时再按需开——这是单点收益最大的一处改动。

### 4.5 聚合层（超节点与聚合边）

**聚合分组直接复用现有资产**：`_clusterKey()`（`:238-243`）与 `_clusterKeys()`（`:246-253`）
已经实现了"制造部门 / 产品大类 / 加工地"三维分组，且处理了"一个编码可属于多个加工地组"
这个麻烦情况。聚合层不需要新写分组逻辑。

聚合节点的字段设计（严格按可加性分类）：

| 显示项 | 是否可聚合 | 说明 |
| --- | --- | --- |
| 编码数 | ✅ | 成员计数 |
| 风险编码数 | ✅ | 布尔或运算，任一成员有风险则计数 +1 |
| 当月单一加工地编码数 | ✅ | 计数 |
| 数据不完整编码数 | ✅ | 计数 |
| 组间连接对数量 | ✅ | 用于聚合边线宽 |
| 缺口 / 供应 / 需求绝对值 | ❌ | **量纲不统一，禁止相加** |
| 缺口分配到某上层 | ❌ | 违反口径，禁用 |

数量类信息的正确表达方式：**个数、最大值、占比、分布直方图**，或统一降级为
"N 个编码存在缺口"（只报个数，不报合计）。

**坐标与防跳变**：超节点坐标 = 成员世界坐标的**质心**。展开时成员坐标不变、无需重新布局，
视觉上就是"地图放大后 POI 炸开"，连续不闪。

**双击语义**：单击超节点 = 选中并显示聚合信息；双击 = 展开到下一层级
（等价于地图点聚合 POI 后放大）。需要与现有"双击下钻到该编码"（`:198-202`）区分：
超节点上没有真实编码，双击应触发展开而非 `onNodeDblClick(code)`。

### 4.6 关键路径跨层连续

这是"既看全局主线、又能下到编码"的答案：

- 聚合边 `critical = 任一成员边 critical`，`risk` 同理（或运算）。
- 聚合边线宽 ∝ 组间存在关键路径的连接对数。
- 效果：L0/L1 上呈现为一条**连续的高亮走廊**，L2/L3 放大后自然落回具体编码。

现有 `criticalPath` 由后端返回（`d.critical?.path`，`forecast-app.js:306`），
聚合层只需在 `_applyHighlight()`（`:394-402`）里把 keep 集合扩展到父级超节点。

### 4.7 状态更新改增量（解"点一下卡"）

现状：`_applyStates()`（`:405-416`）每次点击重建全部 71.4 万个状态 key。

改造：维护 `this._stateOf = Map<id, stateKey>`，只对**变化的元素**调 `setElementState`。

```text
点击编码 A（链路高亮）
  旧：全部节点 + 全部边 → setElementState   （71.4 万次）
  新：diff(上次状态, 本次状态) → 只有变化的元素  （通常 < 1 万次）
```

实现要点：

- 首次或数据变更时做一次全量初始化，之后全部走 diff。
- `dim` 状态从"给非链路元素设 dim"改为"给非链路元素设空状态"——
  两者视觉等价（默认 `opacity: 1`），但 diff 后不需要触碰未变化元素。
- 切染色（`setColorBy`）、切高亮（`setHighlight`）走 `restyle()` 的全量
  `updateNodeData` / `updateEdgeData`（`:466-467`）——**这两处也要改成只更新可见集**，
  否则层级切换后仍会全量重建。

### 4.8 凸包适配

现有实现（`:260-324`）在聚类开启时对大图有真实开销，三处修改：

1. **只对可见成员算凸包**（当前 `:284` 遍历全量 `this.nodes`）。
2. **批量取坐标**：用一次 `getCanvasByViewport` 求变换，自己批量换算，
   替代逐成员 `getClientByCanvas(getElementPosition())`（`:294`）。
3. **拖拽期降频**：当前 `dragLoop`（`:164`）逐帧重建整个 SVG DOM。
   改为复用已有 path 元素、只更新 `d` 属性，或限制到每 2 帧一次。

**语义保持**：分组标签 `${组名} · ${成员数}`（`:312`）**必须继续显示真实成员总数**，
即使视觉上只画了可见成员的凸包。这是"点数量是对的"的直接体现，不能改成"可见成员数"。

### 4.9 修掉 `_usePreset()` 的假开关

```js
// 现状（:362）：>800 节点时，无论 layoutMode 是什么都返回 true
_usePreset() { return this.layoutMode === 'layered' || this.nodes.length > 800; }
```

改造后由 LOD 层级决定是否使用 preset 坐标，`layoutMode` 恢复其字面语义。
需明确"力导向在大图下不可用"是**产品决策**，UI 上应禁用该按钮并给出提示，
而不是让用户点了没反应。

### 4.10 空间浏览模式（二维地图 + 滑动）

**需求**：不搜任何条件时看到全部；可以横向滑动，一路浏览同一个颗粒度下的其他产业 /
制造部门 / 加工地，像地图平移一样连续，而不是"选一个 → 看一个 → 再选一个"。

**这是空间浏览（spatial browsing），不是查询过滤（query filtering）。** 现有系统的交互
都是后者：改筛选 → 重新请求 → `setData()` → 全量重排 → 视口重置。所以用户"滑不出去"。

#### 4.10.1 必须先拆的障碍：世界坐标系现在是"一屏"，不是"一张平面"

`_presetPos()`（`:364-371`）把布局尺寸直接绑定到容器尺寸：

```js
const plan = layered(this.nodes, this.edges,
  Math.max(200, rect.width - 72),      // ← 宽度 = 容器宽度
  Math.max(160, rect.height - 110),    // ← 高度 = 容器高度
  node => this._clusterKey(node));
```

而 `layered()` 内部（`:12-17`）会二分求出一个 `columns`，让整图长宽比**匹配视口**，
最后 `render()` 再 `fitView()`（`:454`）把整图压进一屏。

**结果：整张图刚好铺满视口，左右根本没有可滑动的空间。** 这是"滑不出去"的根本原因，
和性能无关。

同时 `ResizeObserver`（`:172-180`）在容器尺寸变化 120ms 后触发**全量 render + 重排**——
所以展开/收起侧边栏，全图位置就变一次。这与"地图不该动"直接冲突。

#### 4.10.2 目标形态：二维地图

| 轴 | 含义 | 现状 |
| --- | --- | --- |
| **纵轴** | BOM 层（最多 10 层） | ✅ 已实现，`layered()` 按 `level` 分带 |
| **横轴** | 组织维度：制造部门 / 产品大类 / 加工地 | ❌ **未实现**——`group` 参数目前只用于**同层内排序**（`:26`），不是空间分带 |

改造要点：

1. **横轴分带**：把 `group`（即 `_clusterKey()` 的结果）从"排序键"提升为"空间带"。
   每个部门 / 产业 / 加工地分配一个**固定宽度的水平区间**，带内再按 BOM 层纵向排列。
   于是"左右滑动 = 穿过组织维度，上下滑动 = 穿过 BOM 层"。
2. **坐标系与视口解耦**：`layered()` 的 width / height 不再等于容器尺寸，改由
   **数据量决定**（如 `列数 × 带宽`）。容器只决定视口，不决定坐标系。
3. **初始 fitView，之后不自动 fitView**：首次进入给一次全局感，
   之后视口完全由用户控制（`drag-canvas` / `zoom-canvas` 已注册，G6 原生支持）。
4. **尺寸变化保持视口中心**：`ResizeObserver` 改为 `graph.resize()` +
   按原视口中心重新定位，**不再触发重排**。

#### 4.10.3 为什么这一步可以"先做出来"

关键洞察：**这个交互发生在聚合层，而聚合层对象很少，不需要视口裁剪就能自由平移。**

- L0（产业 / 部门 × BOM 层）：假设 20 个部门 × 10 层 = 最多 200 个块；
- L1（再细一档）：假设 100 组 × 10 层 = 最多 1000 个块。

几百到一千个图元，G6 全量渲染毫无压力，**可以随便滑**。这正是地图的规律：
缩小的时候数据天然就少，所以能自由浏览；放大到细节才开始按视口加载。

而聚合块本身**前端就能算**——`/api/graph` 返回的 nodes 已带 `make_dept`、`level`、
`risks`、`single`、`siteCount` 等字段，按 `(组织维度, level)` 分组计数是毫秒级。
所以 **4.10 不依赖后端改造即可先落地**（后端 `aggregation` 参数属于 T2，
首要解决传输量，不是这个交互的前提）。

#### 4.10.4 交互模型（三个动作，互不干扰）

| 动作 | 语义 | 是否重排 |
| --- | --- | --- |
| **平移 / 缩放** | 在同一个数据集内浏览 | ❌ 不重排，只改视口 |
| **缩放跨阈值** | 换呈现粒度（L0↔L1↔L2↔L3） | ❌ 坐标不变，只换渲染集 |
| **筛选 / 切版本** | 缩小数据集 | ✅ 允许重排，但**不重置到无筛选以外的视口** |

必须区分清楚：**筛选是"换一批数据"，平移是"看同一批数据的另一部分"。**
现在两者走同一条 `setData → render → fitView` 路径，所以平移能力被筛选路径吃掉了。

#### 4.10.5 与层级的关系

- 聚合层（L0 / L1）：可自由平移，横向浏览不同部门。
- 网络层（L2）：对象数上升，需要配合 4.2 的视口裁剪。
- 编码层（L3）：必须视口裁剪 + 标签碰撞剔除。

所以"一直左右滑动"在 L0 / L1 上是**立刻能做**的；在 L2 之后才需要视口裁剪兜底。

### 4.11 地图化作为正交能力：覆盖全部维度组合

**需求**：地图化不能只服务"按部门"一个维度。现有全部维度组合都要支持地图式浏览：

- 布局：力导向 / 分层
- 口径：直接父子 / 跨产业 / 最顶层
- 聚类：无 / 制造部门 / 产品大类 / 加工地
- 染色：层级 / 风险 / 加工地 / 无

（2 × 3 × 4 × 4 = 96 种组合）

#### 4.11.1 核心设计：先把维度按"是否决定坐标"分成两类

这是整套设计的地基。四个维度性质完全不同：

| 维度 | 性质 | 决定坐标？ |
| --- | --- | --- |
| **布局**（力导向 / 分层） | 位置生成算法 | ✅ **决定** |
| **空间主轴**（新增） | 横向分带依据 | ✅ **决定** |
| 口径（直接父子 / 跨产业 / 最顶层） | 边的语义 | ❌ 只改连边 |
| 染色（层级 / 风险 / 加工地 / 无） | 视觉编码 | ❌ 只改颜色 |

由此得到一条可以写进不变式的规则：

> **坐标系只由 (布局, 空间主轴) 决定。口径与染色的任何切换都不得改变节点坐标与当前视口。**

这条规则直接兑现了 §2 的"坐标系不变性"：以后用户切"跨产业"、切"风险染色"，图不会跳。

#### 4.11.2 新增"空间主轴"选择器，与聚类解耦

现在"聚类"同时承担了两个职责：**分组（画凸包）** 和 **空间排序（`group` 参数）**。
要支持多维地图化，必须把后者独立出来：

| 选择器 | 职责 |
| --- | --- |
| 聚类（已有） | 画哪些凸包 / 分组 |
| **空间主轴（新增）** | **横向按什么分带** |

这样就能出现很有用的组合，例如：
**空间主轴 = 制造部门（横向分带）+ 聚类 = 加工地（带内凸包圈出加工地）**。
主轴默认值 = 当前聚类维度，所以老用户不会感到变化。

#### 4.11.3 两种布局如何统一到"带"抽象下

已实证：G6 v5.1.1 bundle 的 force 布局**内置 X/Y 轴向约束**
（`getXForceOptions` / `setupXForce`，读取 `forceXPosition` 与 `forceXStrength`，底层为 d3-force）。
所以力导向也能分带，不必为地图化而放弃它。

| 布局 | 分带方式 | 手感 |
| --- | --- | --- |
| **分层** | **硬分带**：坐标精确对齐到带中心，y 轴 = BOM 层 | 规整、可预期，适合大图总览 |
| **力导向** | **软分带**：`forceXPosition` = 带中心，`forceXStrength` 控制约束强度 | 保留拓扑聚散感，同时可横向浏览 |

建议把 `forceXStrength` 暴露为一个可调项（0 = 纯力导向，1 = 强分带），
让用户自己在"探索感"和"地图感"之间找平衡。这同时给"力导向"一个明确的产品定位：
**力导向 = 探索模式（看拓扑聚散），分层 + 主轴 = 地图模式（可浏览）。**

#### 4.11.4 主轴 × 布局的组合矩阵

| 主轴 \ 布局 | 分层 | 力导向 |
| --- | --- | --- |
| 无（单一带） | 等价现状：整图一屏 | 等价现状：自由铺开 |
| 制造部门 | 部门分带 + BOM 层 | 部门软分带 + 自由 y |
| 产品大类 | 大类分带 + BOM 层 | 大类软分带 + 自由 y |
| 加工地 | 加工地分带 + BOM 层 | 加工地软分带 + 自由 y |

八格全部可做，且**共用同一套分带代码**——分带逻辑与主轴的取值无关，
只依赖"分组键 → 带序号"这个映射。这也正是 `_clusterKey()` 已经提供的抽象。

#### 4.11.5 三个必须诚实对待的难点

1. **多加工地编码跨组（主轴 = 加工地时）**
   一个编码可能产出在多个加工地，**无法落在单一带内**。处理方式：
   - **主带分配**：按 `sites[0]` 或占比最大的加工地归入主带；
   - 其他归属用**角标 + 连线**表达（复用 `_clusterKeys()` 的多组能力，
     凸包仍可跨带绘制）；
   - UI 上必须说明"节点画在主带，角标表示同时在其他加工地有产出"。
   这是维恩式交叉在地图化下的必然折中，不能假装没有。

2. **带数差异极大**：制造部门约 20 个、产品大类约 50 个、加工地约 300 个。
   带宽需要按带数自适应；当主轴 = 加工地（300 带）时，横向跨度会非常大，
   **此时必须配合 §4.2 的视口裁剪**，不能指望全量渲染。

3. **力导向的坐标稳定性**：力导向有迭代与随机性，若不处理，
   每次重排位置都变，直接摧毁"地图感"。处理方式：
   **固定随机种子 + 收敛后锁定坐标**（把收敛结果作为 preset 复用），
   之后重绘、切染色、切口径都不再重跑 force。

#### 4.11.6 顺带可以修的一处既有冗余

"染色"与"聚类"的选项里都有 **加工地**。当两者同时选中时，颜色与分组表达同一信息，
视觉上是冗余的。建议：**染色选中与聚类相同的维度时，自动改用风险染色**并给出提示，
或直接在染色中移除重复项。这是个小的产品决策，但会明显影响图的可读性。

## 9. 三角色审视

- **业务方**：缩到全景能立刻回答"哪个加工地 / 哪一层最扎堆"，放大能看到编码。

- **领导**：价值在于从"看不了"变成"能看三层"——总览、区域、编码三级递进，

- **数据科学家**：正确性优先级高于性能。计数守恒可证、布尔风险是或运算可证、

## 11. v2 增补：DAG 多层级归属与 LOD 落地（2026-09-15）

> 本章是"计划管理产品经理"视角对前文的根本性修正——前文所有设计隐含了
> "每个编码有唯一 BOM 层级"的假设，而这个假设**在真实 BOM 下是错的**。

### 11.1 认知修正：BOM 是 DAG 而非树

真实业务确认：**同一编码在不同产品 BOM 里处于不同层级，甚至同一 BOM 内也处于不同层级**
（一个编码既被整机直接引用，又被某个模组引用）。由此产生的三层事实：

| 层 | 事实 | 代码位置 |
| --- | --- | --- |
| 数据结构 | `graph.parents` / `graph.children` 完整保留 DAG 全部父子边，**结构无损** | `forecast-core.js topology()` |
| 层级压缩 | `level` 用 `Math.max(parent.level+1)` 计算，是**最长路径深度**（最坏供应链深度），把多层级归属压缩成了单值 | 同上 |
| 演示数据 | 旧 `demo()` 每层只连上一层，是**假 DAG**（严格分层树），从未暴露多层级现象 | `server/demo-data.js`（已重写） |

**纵轴语义定论**：分带布局纵轴继续用 `level`（最长路径深度）。这不是妥协而是必然——
最长路径深度保证对任意边 `(parent, child)` 恒有 `level[child] > level[parent]`，
即**所有边在纵轴上永远向下**，不会出现"边倒流"。这是拓扑不变量，任何其他深度定义都会破坏它。

### 11.2 多层级归属的完整表达（minLevel / multiLevel）

- `forecast-core.js topology()` 新增 `minLevel`（最短路径深度，BFS 语义），与 `level`（最长）构成区间；
  `minLevel < level` 即该编码跨多个层级归属。
- `server/artifact.js graph()` 重建路径同步计算 `minLevel`（在线/离线两条路径一致，产物格式不变）。
- `server/service.js graph()` 节点出口新增 `minLevel` / `parentCount` / `multiLevel` 三个字段（纯增量）。

**演示数据重写**（`server/demo-data.js`）：1004 编码 / 1902 边 / 7 层，
父项跨 1-3 层（70% 相邻 / 25% 跨 2 层 / 5% 跨 3 层）、每编码 1-3 个父项、
每层前 20% 为共用料池承接 60% 引用。实测 **75.1% 编码为 multiLevel**（754/1004），
真实呈现"同一编码跨多层"的业务事实。

**可视化标记**：multiLevel 节点用金色（#d9a64a）虚线外圈（`lineDash: [3,2]`）标记，
风险节点仍优先用粉红实线描边（风险 > 多层级的优先级）。

### 11.3 LOD 四档落地（语义缩放的实现）

前文只设计了档位，本轮真正落到 `forecast-graph.map.js`：

| 档位 | zoom | 节点 | 标签 | 边 |
| --- | --- | --- | --- | --- |
| L0 战略层 | < 0.28 | (聚类组 × BOM 层) 桶聚合为超节点，size 随 √count | 桶名 · 编码数 | 桶间汇总边（关键路径 teal 骨架） |
| L1 聚合层 | 0.28–0.6 | 全量缩小 ×0.55 | 仅关键编码（选中/风险/multiLevel） | 仅关键边（critical/risk/链路/跨产业）；**无关键边时降级为全量边 × 0.35 透明度** |
| L2 网络层 | 0.6–1.2 | 全量原尺寸 | 仅关键编码 | 全量 |
| L3 编码层 | ≥ 1.2 | 全量 | 全部 | 全量 |

实现要点（踩坑记录）：

1. **`autoFit: 'view'` 必须关掉**——它在每次 `setData` 后强制 fitView，把 LOD 切换时
   `zoomTo(zoom, center)` 的视口恢复完全覆盖（实测 zoom 被打回 0.198）。fitView 改由
   `render()` 首帧手动执行（`_didInitialFit`），力导向与分层统一处理。
2. **边 id 保持原始索引**（`'__e'+i`）：L1 过滤边后若用新索引，`_applyStates` 回填状态会
   引用未渲染边，G6 抛 `Unknown element type`。配套 `_renderedEdgeIdx` 记录渲染边集合。
3. **G6 初始化时序**：`initRuntime → transform → aftertransform` 会在 graph 就绪前触发，
   `_detectLod` 的 `getZoom()` 必须 try-catch（实测 `vJ.getZoom` 读 undefined）。
4. **L0 聚合块是虚拟节点**（`__lod0_*`）：`_applyStates` 在 L0 短路返回（虚拟 id 不参与
   真实编码状态），`restyle` 在 L0 退化为完整重建。桶信息由 `layered()` 新增返回 `buckets`。
5. **无死循环**：`_applyLod` 不 fitView；`zoomTo` 恢复后 zoom 与档位一致，`_detectLod` 幂等。

### 11.6 回归修复记录（Windows IPC 竞态，2026-09-15）

本轮 demo-data 重写为 1004 编码真实 DAG 后，`ui-browser.js` 的"issue download after import"
回归超时。定位为 **Windows 下 build.js 子进程发送结果后立即 disconnect/exit 的 IPC 竞态**：

- **现象**：folder 导入的 build job 报「构建进程退出（0）」，失败 job 无 `issues` 字段 →
  无 `#build-jobs a[href*=issues]` 链接 → 测试 `wait()` 超时。
- **根因**：`child_process.fork()` 下 `process.send({result}, () => process.disconnect())`
  的回调触发仅表示消息已写入内核管道，不代表父进程已读取；紧接的 `disconnect()`/`exit`
  关闭管道导致结果消息丢失。子进程 stderr 显示 `result flushed`，但父进程
  `hasMessage=false`、exit code=0 → reject「构建进程退出（0）」。`.unref()` 兜底定时器
  不保持事件循环存活，无法兜底。
- **修复（握手模式）**：`server/build.js` 子进程发送终态消息后**不再自行退出**，改由
  `server/build-jobs.js` 父进程在 `message` 事件收到 result/error 时主动
  `child.disconnect()`；子进程监听 `disconnect` 触发 `process.exit(0)`，并保留一个
  **非 unref** 的 30s 兜底定时器确保事件循环存活到结果被真正读取。
- **连带修复**：`forecast-app.js:341` folder 扫描异步回调加 `if (dir/files)` 判空
  （import 后 render() 重渲染 + 切 overview 后 `$('folder-files')` 为 null 抛
  `TypeError: Cannot set properties of null`）；`tests/http.test.js:44` 断言 240→1004。
