# 后端深度审查与性能验证

本轮只修改后端、测试与说明文档；前端文件未改。核心目标是减少重复工作、隔离慢任务、保证数据版本一致，并提供可核验的业务洞察。前端实施建议见 [前端改善建议与洞察接入任务书](前端改善建议与洞察接入任务书.md)。

## 已修复的问题

| 问题 | 修改 | 作用 |
| --- | --- | --- |
| 不传版本时，每次扫描132万行预测获取最新版本 | 从产物清单直接定位预测版本 | 单编码查询不再随整张预测表增长 |
| 选中单编码仍生成12万编码全网明细 | 图谱按邻接表和所需节点读取矩阵 | 单编码图查询保持局部工作量 |
| 翻页反复统计、筛选、排序 | 每个引擎缓存两个上下文的有序列表、统计及最多四组过滤结果 | 同口径翻页复用索引，缓存绑定不可变引擎 |
| 报告重复扫描、排序和构造热力数据 | 同上下文缓存报告业务结果，trace重新生成 | 重复查看报告复用结果 |
| 下层查询额外调用预测口径全网计算 | 根据可达节点传播系数并读取对应forecast/mo矩阵 | 指令口径不再顺带生成另一份全网结果 |
| 表分页每次扫完整表 | 已装载表直接切片，编码过滤建立有界缓存索引 | 大表翻页不全表遍历 |
| 单编码推演为所有编码月份建立临时修改索引 | 只索引请求涉及的编码月份 | 减少无关JSON键、数组和临时内存 |
| 每次推演重新校验不变的BOM拓扑 | 已校验不可变基线只检查允许变动的数量/日期，不做结构重算 | 避免不可能发生的结构重算；表2剔除量与预测相互独立，不再复核大小关系 |
| 构建收到结果消息就启动下一进程 | 等进程退出再推进构建队列 | 避免两个多GB构建堆重叠 |
| 装载前没有有效队列上限；请求可能一直等 | 独立Lane管理器，装载期同样限流，排队/执行计时 | 最多32项等待/执行请求，超时明确反馈 |
| 请求断开后队列仍保留无用任务 | HTTP取消信号传入Lane | 未执行的过期读请求直接移除 |
| 查询线程挂死后无自动恢复 | 执行超时终止失效线程并重新装载已提交版本 | 控制接口继续可用；重试不会得到半份结果 |
| 切版本时排队请求可能临时转读新版本 | 请求入队时固定修订号，原线程排空后退出 | 同一请求结果保持版本一致 |
| 表查询忽略指定历史修订号 | 表接口按revision选择产物 | 不再把当前表伪装为历史表 |
| 网络重试再次提交产物 | 同一身份＋previewId复用运行中/已完成装载任务 | 不重复发布版本；任务保留期内可安全查询原结果 |

算法数值矩阵与共享业务核心没有改变，本轮不会因查询优化而要求已有同算法产物重建。重启服务即可使用新接口；旧版单块快照迁移仍按此前说明显式重建。

## 新增业务洞察

`GET /api/insights` / 模型工具 `summarize_code` 提供供应缺口、上层贡献、当月下层总量风险、三口径比较、本编码未来月份、库存覆盖、加工地和周期事实，以及建议查看的证据和可填写到推演表单的参数。

结论是确定性规则生成的业务解释，`generator.llmUsed=false`；本轮没有调用外部大模型。它保证同一组输入得到同一组事实，有完整trace和证据。风险与未知可以同时存在；缺库存不否定已经算出的预测匹配结果。不会将共享料总缺口分配给所选上层，也不会自动推定哪个产业预测虚高。

缓存按引擎及编码/月/范围/来源/窗口绑定，每个引擎最多32份洞察。情景归属验证发生在取缓存之前，不能通过缓存越权读取另一身份的情景。

## 同规模HTTP对照

本机Node v24.19.0，约16GB内存；同一份已构建产物：12万编码、59.4万BOM边、132万预测行、11个月、10层、300加工地。前后均使用新建独立目录库与新服务进程，按相同顺序执行。下表除特别注明外为重复请求的中位数，包含HTTP传输和结果解析。

| 操作 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 单编码局部图首次请求 | 728ms | 14.5ms |
| 翻页，不传预测版本（15次） | 143ms | 5.8ms |
| 翻页，显式预测版本（15次） | 86.5ms | 10.3ms |
| 加工地筛选（10次） | 88.4ms | 9.9ms |
| 单编码11个月详情（10次） | 65.2ms | 6.6ms |
| 上层编码详情（5次） | 73.2ms | 14.3ms |
| 需求方下层风险（5次） | 78.6ms | 16.4ms |
| 报告（5次） | 110.3ms | 14.4ms |
| 8个并发列表请求全部完成（3组） | 1106ms | 14.4ms |
| 首次单编码推演，含独立线程冷装载 | 12.55s | 11.13s |

新增洞察首次请求：底层编码11.8ms、上层编码16.1ms；后续推演中位数约2.17s，3次范围1.98–2.43s。运行期间182次健康请求最大约17.4ms。服务RSS在完成推演后一次采样约4.22GB；这是进程时点值，不是全过程峰值，也不包括离线构建子进程。

需要公平理解冷缓存：优化前单编码图已先生成全网明细，所以其后列表首次请求仅152ms；优化后局部图不再提前做这份工作，随后第一次全网列表需要758ms。局部查询提速没有消除第一次全网结果装饰成本。优化后翻页P95约15.3ms，样本仅15次，不能当作生产长期SLA。HTTP计时还受Windows调度、缓存和机器负载影响。

原始结果位于 `test-output/response-before.json`、`test-output/response-after.json`。这些生成文件不入版本控制；对照脚本入库，可在同机复现。测试未修改业务数据库。

另一次真实在线更新测试：保留12万编码在线基线，后台完整重建并装载新版本，同时每250毫秒发起业务详情查询。重建与切换约30.09秒（含轮询及切换后的观测时间），118次查询全部成功，最长18.67ms；响应分别携带旧修订号1或新修订号2，业务数值一致。候选线程装载约7.82秒，结束时无遗留构建进程/装载线程。结果见 `test-output/version-switch-benchmark.json`。此测试覆盖并发读与版本切换，不代表同时运行多个大情景的峰值资源测试。

## 推演冷启动的处理

为保持查询流畅，推演使用独立线程，首次调用需要装载自己的基线。不能将这11秒描述为所有模拟都只需毫秒。

新增 `POST /api/scenarios/prepare`（planner及以上）可在前端进入推演区域时提前准备。请求接受revision/version/month，返回后台任务。这样用户填写参数时可以并行装载；准备完成后实际模拟复用基线。此接口不会发布版本、创建情景或修改数据，也不保证经过版本切换/缓存淘汰后永远保持热状态。

## 运行可观测性与边界

- `/api/health` 是存活检查；`/api/ready` 在读线程装载完成时返回200，未就绪返回503。
- `/api/diagnostics` 仅管理员可读，包含目录修订号、线程排队/失败/超时次数、最近128次线程调用的P50/P95、装载耗时、事件循环延迟、内存和磁盘余量。
- 每个HTTP响应携带 `X-Request-ID`，错误正文也携带requestId。业务查询trace另含构建ID，以区分请求追踪与数据追溯。
- 默认查询时限30秒（含排队），推演时限120秒，装载时限120秒；分别通过 `QUERY_TIMEOUT_MS`、`SIMULATION_TIMEOUT_MS`、`LOAD_TIMEOUT_MS` 调整。活动读请求即使客户端断开，也受原执行时限约束。
- 超时会清退该线程的请求并重新装载，不自动重放用户的写入。已保存情景在极窄的“保存完成但响应尚未到达”窗口仍可能存在，不能把超时等同于事务回滚。基线产物提交可按原previewId获得同一个任务结果。

当前仍是单机、单在线查询线程＋独立推演线程＋串行构建进程。历史版本、双版本装载和大规模模拟会增加内存；没有承诺无限数据、任意并发或分布式高可用。对于更密集网络、多版本和多人使用，应以真实数据重复压测；不要只按编码数估容量。

## 尚需产品和数据决定的能力

1. **跨版本风险变化归因**：需拆分预测、BOM、库存及口径变化的贡献，不能从一个总缺口差额直接猜原因。
2. **周期时移与日级履约**：当前同月匹配及周期最长路径不能代替投料/完工日历、运输与在制分析。
3. **计量单位与产能**：没有正式单位、产能和合格加工地数据时，不应跨编码加总数量或承诺增产可行。
4. **风险处理闭环**：关注清单、负责人、复核记录、处理状态需要员工级身份和独立业务记录，不能写回基线计算结果冒充处理完毕。
5. **多用户生产部署**：企业认证、授权隔离、一致性备份与恢复演练、资源告警、远程代理超时配置，仍需结合部署环境落实。
6. **AI问答**：已有事实和工具接口；外部模型选择、密钥、审计及回答事实校验尚未配置。无需让外部模型成为基本查询的前置条件。
